The Road of a Memory

A conversation becomes an archive, then source-linked notes. The notes form a graph of subjects, people and lessons. Memory comes back when it matters, and a doubtful note can always be checked against the original words.

Public architecture, pre-release. This is an adapted public copy of the flow, not a claim that the exported engine or installer is ready. The first target is one Linux machine; model APIs are explicit choices.

A. Keep the Conversation

Native session adapter and local document archive

  1. 01
    Person and assistant talk

    The native session writes the conversation. An adapter preserves who said what, when, and which exact source record it came from. Different substrates need their own tested adapter.

  2. 02
    Import and prove the copy

    Records enter the archive with stable IDs. Read-back proves the copy before it counts as saved. Re-importing the same data adds nothing; a conflicting record is reported, never silently overwritten.

  3. 03
    A reset closes a window

    A compaction summary ends one stretch of conversation. A session that ends without compacting gets a separate closing marker so its last words are not lost. Snapshots wait in a local spool until their archived copies are verified.

  4. 04
    Some notes take the short road

    A manually recorded fact, mistake or lesson can go straight to the memory store, with its original source kept. Capturing the same turn again must not duplicate it.

A closed window is available to process

B. Turn a Window Into Notes

Local Vulkan model or an explicitly configured API; CUDA is a later backend

  1. 05
    Select unfinished work

    Resume half-finished windows first. A window is complete only when its required stages are complete, not merely when extraction has produced some notes.

  2. 06
    Keep attributed dialogue

    Separate the person's and assistant's words from tools, injected instructions and transport envelopes. Tool output is not a statement by the person. Mask secret-shaped material before sending model input.

  3. 07
    Bind short answers, then split

    An answer such as "the second option" is tied to the list it answers. Dialogue is divided into bounded chunks without losing its source references.

  4. 08
    Write short, cited notes

    The extraction model produces notes with their kind and exact source rows. Each completed chunk is saved immediately. Failures remain visible and resumable; an API model needs an explicit model identity, not a local-file assumption.

Raw notes retain the way back to the conversation

C. Put Notes Into the Graph

Local encoder and graph store

  1. 09
    Encode the meaning

    An encoder turns each note into vectors for grouping and search. Long notes get additional pieces so an important clause at the end can still be found.

  2. 10
    Check for a repeat

    A close older note is compared with the new one: same event, same claim again, a changed state, or different. Repeats keep their own source and date under the existing note instead of manufacturing a new memory.

  3. 11
    Keep exact names and topics

    Code records identifiers such as projects and issue references. Similar notes join topic groups. Trust, event dates and provenance stay visible; an unverified note is not promoted to certainty.

A note exists, with meaning and source

D. Connect What Was Learned

Configured strong, middle and light judging roles

  1. 12
    Link advice to activities

    A note about a failure or a constraint is linked to the activity before which it matters. Merely mentioning an activity is not enough.

  2. 13
    Build lessons and name subjects

    Repeated advice with the same mechanism and correction becomes a lesson, with each event kept beneath it. A short subject name helps search find what a note is about even when its wording is indirect.

  3. 14
    Build people and thing cards

    Notes connect to entities and their cited, dated cards. Ambiguous names are asked about rather than guessed. A newly stated fact can update a card only when its source supports it.

Notes, lessons and cards share one connected store

E. One Connected Memory

Local graph database; original conversations remain in the document archive

  1. 15
    Keep the relationships

    Notes connect to occurrences, pieces, topics, exact names, activities, lessons, entities, cards and checks. The graph is an index to experience, not a replacement for the original conversation.

  2. 16
    Keep identities separate

    Every instance owns its records and local identity boot file. Remote requests are checked against the service's own bearer token and ownership rules, even when no proxy is present.

A message, an action or an explicit question asks for memory

F. Find Relevant Evidence

Local services by default; optional authenticated remote access

  1. 17
    Search three ways

    Meaning, exact words and exact identifiers contribute candidates. Finding a note through more than one route can raise it; one search method does not erase the others.

  2. 18
    Apply relevance and trust

    Notes below configured closeness or trust floors do not arrive as ordinary evidence. A doubtful note is labelled as doubtful. A failed search is reported as unavailable, not "nothing remembered".

  3. 19
    Order the page

    A separate reranker improves the order. Additional pages remain available. Encoder and reranker requirements do not disappear when extraction uses an external API.

A bounded set of dated notes is ready to return

G. Bring Memory Back at the Right Moment

Native lifecycle hooks and explicit operation commands

  1. 20
    At start, on a message, on a name

    Session start brings identity and relevant open items. A message can bring close notes; the first mention of an entity can bring its card. Per-session budgets prevent endless repetition.

  2. 21
    Before an action, after an error

    Applicable lessons arrive before a change, not every harmless read. After a tool failure, the failure's context can find relevant past experience. Each substrate must prove these hooks natively.

  3. 22
    Read deeply with a briefing

    A briefing reads a subject's notes and cites them, keeping contradictions and uncertainty explicit. Notes past a reading limit are marked unread. Read tokens prove required files were read; changed briefings can be rebuilt across compaction.

  4. 23
    Keep pictures with provenance

    Optional picture memory keeps content, descriptions and links to notes. Newly pasted images wait in a local pending area until explicitly kept or dropped. No private network share is a default requirement.

Memory informs the answer, and the answer becomes new experience

H. Check and Correct

Turn-end review, original source records and per-window checks

  1. 24
    Review usefulness and doubt

    Delivery is not proof of usefulness. Suspect notes and unresolved activity/entity questions enter a paced review queue. Briefing suspicions are requests to check, not automatic truth.

  2. 25
    Open the original and record a verdict

    The assistant reads the note's actual source, then records right, partly right, wrong or outdated, with evidence. A wrong link can be corrected separately. A changed fact remains dated, not erased from history.

  3. 26
    Prove the loop works

    Track whether mistakes were captured, corrections reached the store, and relevant lessons returned later. Interrupted stages remain visible. The next conversation starts the same loop again.

This chart describes the public copy's target flow. It contains no personal archive or private infrastructure map. Runtime readiness and supported backends are stated in the repository README.
